See `milestone-1-report.md` for final checks and remaining verification; unchecked boxes below are the original audit checklist, not a final status report.

Read-only source review of `.upstream/FreshRSS` tag `1.30.4`, `.upstream/Extensions/xExtension-LlmClassification`, and the files appearing under `xExtension-ArticleTopics`. No source was changed by this audit. The implementation is still in progress; findings below refer to the snapshot read and should be rechecked as files continue to land.

## Findings for the implementation

### 1. `_entrytag` and ownership must share one atomic commit

FreshRSS label associations are rows in `_entrytag`, with `(id_tag,id_entry)` as the primary key and foreign keys cascading on deletion in all three schemas: `app/SQL/install.sql.sqlite.php:96-103`, `install.sql.mysql.php:105-113`, and `install.sql.pgsql.php:95-102`. The target table is per-user because FreshRSS initializes that user's context/database before the worker; do not hold one cross-user PDO connection or persist bare entry IDs without a user scope.

`FreshRSS_TagDAO::tagEntry()` inserts an association but only returns success/failure; on MySQL its helper becomes `INSERT IGNORE`, and it does not say whether this call inserted a row or encountered an existing one (`app/Models/TagDAO.php:304-324`; `sqlIgnoreConflict()` at 8-10). Thus, calling `tagEntry()` and then recording ownership separately can misclassify a pre-existing/manual association, or crash after inserting the pair but before the ownership record. Retrying cannot distinguish those cases by inspecting the now-present pair.

**Action:** keep ownership and `entrytag` in one transaction on FreshRSS's active user PDO. Before mutation, check for the pair inside that transaction; if present, treat it as manual and do not record it. If absent, insert pair and ownership row, then commit both together. On a concurrent duplicate, roll back/re-read and leave it unowned. Ensure extension tables use that same connection/transaction and are InnoDB on MySQL. Do not rely on “write intent first, then infer after crash”: intent alone cannot prove who inserted the association. A JSON file cannot participate atomically with a SQL transaction; if file state is retained, do not make it the authority for ownership mutations.

Core transaction wrappers delegate to PDO (`lib/Minz/ModelPdo.php:153-168`). `FreshRSS_EntryDAO::cleanOldEntries()` excludes entries with *any* `_entrytag` association when `keep_labels` is on (`app/Models/EntryDAO.php:815-818`), so retention cleanup must remove only extension-owned pairs, and should remove corresponding ownership metadata atomically (or tolerate FK cascade when entry deletion occurs).

### 2. Portability: use a portable schema or per-user files, not ad hoc SQL dialect

The core maintains separate SQLite, MySQL, and PostgreSQL DDL (`app/SQL/install.sql.{sqlite,mysql,pgsql}.php`). Types/identity differ (`INTEGER PRIMARY KEY AUTOINCREMENT`, `INT AUTO_INCREMENT`, `SERIAL`; `_entrytag.id_entry` is `BIGINT`), and FreshRSS's own query layer has driver-specific implementations. A new extension table needs explicit supported DDL for all three drivers, proper primary/foreign keys, and MySQL InnoDB. Do not copy core's backtick quoting or MySQL `INSERT IGNORE` into generic SQL.

For pair insertion, either use `FreshRSS_TagDAO::tagEntry()` and perform the existence check plus ownership transaction carefully, or write driver-specific conflict-safe SQL (`INSERT OR IGNORE`, `INSERT IGNORE`, `ON CONFLICT DO NOTHING`) behind a tested adapter. Since the contract specifies small per-user state in `DATA_PATH/extensions-data/ArticleTopics/<username>/`, files avoid cross-database DDL and sequence portability, but they do not solve atomicity with SQL labels. Keep ownership DB-side if strict crash-safety is required.

### 3. Labels are safe to create through TagDAO; collision checks need canonical names

`FreshRSS_TagDAO::addTag()` itself refuses exact same-name categories with `WHERE NOT EXISTS`, trims and truncates to FreshRSS's indexed length, and returns `false` if it did not insert (`app/Models/TagDAO.php:20-50`). `updateTagName()` applies the same category exclusion (`:67-88`). It is therefore useful as a final guard, but not a substitute for UI validation: report the collision clearly and validate the *final prefixed, trimmed, length-limited label string* before storing config. Compare names with FreshRSS's database collation semantics when checking proactively; MySQL's `utf8mb4_unicode_ci` is case/accent insensitive (`app/SQL/install.sql.mysql.php:99-103`), while SQLite/Postgres behavior can differ. Tag name uniqueness is also enforced by the DB.

### 4. Do not classify in pre-commit hooks; refresh IDs are assigned at batch commit

`EntryBeforeInsert` and `EntryBeforeAdd` appear before `commitNewEntries()` in refresh/import paths (`app/Controllers/feedController.php:678,717,747`; `app/Controllers/importExportController.php:615,632,659`). SQLite assigns committed IDs using `rowid + (MAX(id)-COUNT(*))` during `EntryDAOSQLite::commitNewEntries()` (`app/Models/EntryDAOSQLite.php:87-101`); PostgreSQL likewise calculates rank and row_number in `EntryDAOPGSQL.php:86-101`; MySQL's base DAO calculates rank from `_entrytmp` in `EntryDAO.php:265-...`. A hook-time ID or temporary ID is not a durable article ID.

The ID allocator's max/rank calculation also means a high-water cursor alone is unsafe under overlapping refreshes: a refresh can stage temporary rows and commit after another batch's IDs have been assigned. Use the durable post-commit discovery/reconciliation described in `docs/implementation-contract.md`; do not advance a cursor based only on a seen maximum. Discovery needs to be idempotent and recover if the process exits after DB commit but before writing its external ledger. Where possible, discover from committed `_entry` rows on worker runs; the hook is only an optimization.

`FeedsAfterActualize` is the appropriate hook for observing committed results, but it is not a sufficient durability boundary if extension work there can fail after core has committed. Confirm the hook order in every refresh path before relying on it; the current worker reconciliation is essential. For the proposed standalone CLI, use FreshRSS's standard bootstrap: `cli/_cli.php`'s `cliInitUser()` initializes the requested user via `FreshRSS_Context::initUser()` (`cli/_cli.php:28-40`). The shipped `cli/actualize-user.php` calls `cliInitUser()` and maintenance hooks, and explicitly commits entries (`cli/actualize-user.php:23-43`). Do not bootstrap only the system context and then access DAOs.

The `FreshrssUserMaintenance` hook is called by `cli/actualize-user.php` (lines 35 and 41) and in `javascriptController.php:32`, but that does not prove it runs in the separate cron script `app/actualize_script.php`. Do not depend on it for correctness or retention unless the exact script call path is verified; use the extension's own scheduled worker for this milestone.

### 5. Admin config security: use the global CSRF guard and preserve blank secrets

`extensionController::configureAction()` resolves the extension, blocks non-admins for system extensions, then invokes `handleConfigureAction()` (`app/Controllers/extensionController.php:131-155`). FreshRSS's request bootstrap rejects POST without a valid token (`app/FreshRSS.php:75-78`) via `FreshRSS_Auth::isCsrfOk()` (`app/Models/Auth.php:228-234`); `FreshRSS_Auth::csrfToken()` is the form helper. The base `Minz_Extension::handleConfigureAction()` only migrates the extension user path (`lib/Minz/Extension.php:141-143`), it does not itself validate CSRF. Do not implement an unguarded alternate endpoint or accept config writes on GET.

The reference `xExtension-LlmClassification/extension.php:67-...` demonstrates extension-local POST configuration and per-user values. In the current ArticleTopics config, `configure.phtml:3` correctly includes the CSRF token and `:11` says a blank API key keeps the saved key; however `extension.php:46` unconditionally stores the submitted (blank) key, so saving any other setting clears the credential. Retain the existing key when the submitted key is blank. The secret is not rendered in the current template and should not be logged.

### 6. Retention defaults make topic labels a data-retention change

FreshRSS config exposes `archiving.keep_labels` and `archiving.keep_period` (`app/Models/UserConfiguration.php:6`; defaults in `config-user.default.php:12-18`). The default for `keep_labels` is `true` and `keep_period` is `P3M` in 1.30.4. With that setting, any article with any label is excluded from age-based deletion (`app/Models/EntryDAO.php:815-818`); `keep_period` adds the `lastSeen` cutoff (`EntryDAO.php:841-847`). A topic label on every article therefore prevents ordinary purging unless extension-owned labels are removed first.

Milestone 1 should avoid mass labeling/backfill and should not silently override the user's FreshRSS retention setting. For the planned retention feature, default the extension-owned label lifetime to the user's `keep_period` when set; when there is no period, require a documented explicit age or clearly state that owned labels remain retention-protecting. Purge only recorded extension-owned associations, never manual labels. This is scheduled for Milestone 2 in the prompt, so mark it deferred rather than implying it is already handled.

## Immediate implementation checklist

- [ ] Keep `(entry_id,label_id)` association and ownership insertion/deletion in one transaction on the same per-user PDO connection.
- [ ] Do not claim a pre-existing association; `tagEntry()` does not report insert-vs-ignore.
- [ ] Treat external ownership files as non-atomic unless they are only a rebuildable cache.
- [ ] Bootstrap worker with `cli/_cli.php` and `cliInitUser($username)`; validate the username as a real FreshRSS user.
- [ ] Keep pre-commit hooks free of durable ID/label writes; reconcile committed `_entry` IDs in worker.
- [ ] Preserve manual labels during reclassification and retention cleanup.
- [ ] Enforce category collision after applying the configured prefix and FreshRSS name normalization/length.
- [ ] Ensure extension table DDL and conflict handling cover SQLite, MySQL/MariaDB, and PostgreSQL if SQL storage is chosen.
- [ ] Make retention behavior explicit in docs/config before enabling broad automatic labeling.
- [ ] Confirm config changes rely on the FreshRSS extension handler's auth/CSRF flow.

## Concrete issues in the current ArticleTopics snapshot

These findings apply to the files as read during this audit and should be rechecked as the implementation lands.

1. **Ownership journal and `_entrytag` are non-atomic, and current recovery claims false ownership.** `lib/ArticleTopicsWorker.php:93-132` loads `owned.json`, checks current labels, persists a journal at 124-125, then calls `tagEntry()` at 126. If the call fails or another actor inserts the pair between the check and insert, a retry sees the journaled pair and can later treat it as owned (`:119-125`), deleting a manual label during reclassification. Conversely, a crash after SQL insert but before the next JSON update creates a cross-store inconsistency. `tagEntry()` uses MySQL `INSERT IGNORE` and has no inserted-row result, as covered above. **Fix:** put ownership and association in one same-PDO transaction (or choose a DB design that makes successful association insertion and ownership provenance atomic); do not promote an intent journal to proof of ownership. This is the highest-priority correctness issue.
2. **API key is cleared by any save.** `extension.php:46` writes the posted key even when blank, while `configure.phtml:11` explicitly promises blank means keep saved key. Preserve prior value for blank input.
3. **Collision check does not match FreshRSS normalization.** `ArticleTopicsStore.php:52-64` compares lowercase names after trimming the combined prefix/topic, but does not apply the same 191-character truncation as `TagDAO::addTag()` (`app/Models/TagDAO.php:36-37`) or MySQL accent-insensitive collation. A long prefixed topic can be truncated into a category collision at insertion; case folding alone can also disagree with DB equality. Check the exact final stored label against category DAO names using an explicit consistent normalization, and reject values that would be truncated ambiguously.
4. **Config write is not transactional.** `extension.php:42-52` saves individual settings before enabling-state initialization. If validation/initialization fails later, the user can receive an error after some values have already changed. Parse and validate the complete candidate config and initialize required state before mutating settings, or stage/restore values on failure.
5. **Retention remains unimplemented, with current label writes affecting purge.** `ArticleTopicsWorker.php` has no retention pass; `EntryDAO::cleanOldEntries()` confirms any `_entrytag` protects an article when `keep_labels=true`. Implement owned-label expiration in the planned milestone before broad labelling, and test that manual labels are never touched.
6. **Refresh discovery can be incomplete and is file-racy.** `ArticleTopicsStore.php:82` reads at most 1,000 IDs above the cursor, saves `pending` at 86. If more than 1,000 committed IDs exist and the worker processes that batch while cursor advances, later IDs can be found on the next scan, but concurrent hook/worker writers can overwrite each other's state because `writeState()` (`:99-105`) has only a per-write file lock, not a read-modify-write lock. `FeedsAfterActualize` is best-effort; worker reconciliation is necessary. Lock state mutation across read/reconcile/write, or move discovery to a durable source. Ensure pagination drains all committed IDs before treating a scan as complete.
7. **Current path conventions do not match the implementation contract.** Core `getExtensionUserPath()` resolves to `USERS_PATH/<user>/extensions/<entrypoint>` (`lib/Minz/Extension.php:186-189`); the worker uses the same layout at `ArticleTopicsWorker.php:11`, while `docs/implementation-contract.md` says `DATA_PATH/extensions-data/ArticleTopics/<user>`. Pick one. Prefer the FreshRSS extension user path for config-adjacent files, or update the contract and ensure the CLI uses the exact same path.
8. **Cursor state lacks defensive validation and deletion can loop through many IDs.** `ArticleTopicsStore::readState()` trusts decoded field types except schema and casts pending values to ints (`:89-96`). A corrupt/negative/oversized state can create invalid work or coercion. In `Worker::run()` deleted IDs are removed without incrementing `$processed` (`:34-39`), so the 20-second deadline is the only bound for a long run of deleted IDs. Validate shape/ranges and count skips against the per-run budget.
9. **CLI bootstrap is correct; add user validation and behavior tests.** `cli/classify.php:5,19` loads FreshRSS `_cli.php` and calls `cliInitUser()`, matching upstream. Its `--limit` validation is bounded (`:20-21`). This is the right per-user database bootstrap; preserve it and test a valid user, unknown user, disabled extension, and a failed provider response.
